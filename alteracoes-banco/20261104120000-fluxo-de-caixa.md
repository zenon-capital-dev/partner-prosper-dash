# 20261104120000: fluxo de caixa

**Aplicar:** `supabase/migrations/20261104120000_fluxo_de_caixa.sql`, sem alterar.

**Depende de:** `20261103200000` a `20261103260000`. Só aplicar depois de `20261103260000`.

**Publicar o site só depois desta migration.** O código da `main` já chama estas funções. Sem elas, a tela de fluxo de caixa e os recebimentos não funcionam.

## Tabelas novas

Todas com RLS. Leitura só para quem pode ver o caixa. Nenhum usuário grava direto: toda gravação passa pelas funções.

| Tabela | Para que serve |
|---|---|
| `cash_accounts` | Contas. Cria a "Conta principal" como padrão |
| `cash_permissions` | Quem vê o caixa além de admin e super admin |
| `cash_opening_balances` | Saldo real em uma data. Vale o mais recente de cada conta |
| `cash_other_income` | Entradas que não vêm de venda |
| `cash_settlements` | Livro de caixa: todo dinheiro que entrou ou saiu |
| `cash_sale_adjustments` | Registro de vendas recorrentes antigas convertidas para valor total |

## Funções chamadas pelo sistema (`public`)

`cash_can_access`, `cash_settle`, `cash_receive_for_sale`, `cash_reverse`, `cash_reverse_source`, `cash_refund_payment`, `cash_convert_monthly_sale`, `cash_confirm_historic`, `cash_create_entry`, `cash_cancel_income`, `cash_set_opening_balance` e `cash_month`.

**Novas:** `can_access_cash`, `can_operate_cash`, `cash_settlements_append_only`, `cash_today`, `cash_default_account`, `cash_net_settled`, `cash_mirror_source`, `cash_reverse_amount`, `cash_split_no_auto_paid`, `cash_guard_source`, `cash_capture_payment`, `cash_capture_expense`, `cash_capture_split`, `cash_capture_commission`, `cash_obligations` e `cash_movement`.

## Efeitos nos dados e nas regras

**A migration grava dados ao ser aplicada.** Ela copia o histórico para `cash_settlements`, sem mudar nenhum valor antigo:

- Parcelas pagas ou com valor pago entram como entrada. Parcela em aberto com valor pago entra, mas sinalizada como não confirmada.
- Despesas pagas entram como saída.
- Repasses marcados como pagos entram como saída **não confirmada e fora do saldo**, porque o sistema antigo marcava pago na primeira parcela do cliente, sem pagamento real.

**O que deixa de ser permitido depois de aplicar:**

- Excluir ou cancelar parcela, despesa ou repasse com pagamento lançado. É preciso estornar antes.
- Reduzir o valor de um registro para menos do que já foi pago.
- Alterar ou excluir linhas do livro. A correção é sempre um estorno, que é outra linha.
- Lançar pagamento com data futura.
- Receber valor acima do saldo em aberto.

**Campos antigos:** `payments.amount_paid`, `expenses.paid` e o status dos repasses continuam existindo, mas passam a espelhar o livro.

## Depois de aplicar

- Informar o saldo real em uma data, na tela de fluxo de caixa. Sem isso, os saldos não aparecem.
- Vendas recorrentes antigas gravadas com valor mensal: a correção é feita venda a venda, com `cash_convert_monthly_sale`, só depois de cada confirmação. **Essa migration não faz isso sozinha.** O script com as vendas confirmadas tem identificadores reais e fica fora deste repositório.

## Telas que dependem

`src/lib/cashFlow.ts` chama as funções acima, e as telas de caixa e de recebimentos dependem dele.

## Como conferir

1. Rodar `alteracoes-banco/conferir-banco.sql`. A linha `RESUMO` de `20261104120000` não pode ter `FALTA`.
2. Rodar esta conta. Precisa voltar `1`:

```sql
SELECT count(*) AS contas_padrao FROM public.cash_accounts WHERE is_default;
```

3. Ver o que foi copiado do histórico:

```sql
SELECT source_type, verified, count(*) AS linhas, sum(amount) AS total
  FROM public.cash_settlements
 WHERE origin = 'historico'
 GROUP BY source_type, verified
 ORDER BY source_type, verified;
```

## Como voltar atrás

Não há script de reversão, e o livro não aceita exclusão. Se algo sair errado depois de gravado, restaurar o backup feito antes de aplicar.
